# ムダ・ムラ・ムリをデジタル作業に読み替える

以下はTPSを着想源とした **本スキル独自の例示**。全項目を該当判定するための点数表ではない。品質確保に必要な「検査」や、利用者を助ける「説明」は、価値があるなら残す。

| 典型的なムダ | デジタル作業での観察可能な例 | 誤って削除してはいけないもの |
|---|---|---|
| 作りすぎ | 求められていない20案、用途がない図表、過剰な下書き | 必要な代案、判断に不可欠な証拠 |
| 手待ち | 担当確認の往復、出力待ちの依存関係、承認の滞留 | 明示的なユーザー承認、セキュリティレビュー |
| 運搬 | サービス間の二重転記、コピーと貼り直し | バックアップ、監査ログ |
| 加工 | 同じ文章を別々のスキルで繰り返し推敲 | 独立した校閲、回帰テスト |
| 在庫 | 着手されない大量の課題、読まれない資料 | 長期保存が必要な記録、候補の比較情報 |
| 動作 | クリックが多すぎる操作、同じ情報の再検索 | 自発的な確認、使いやすさを守る選択 |
| 不良 | 誤情報、リンク切れ、テスト失敗、公開後の訂正 | 出典照合、障害時のフェイルセーフ |

## ムラ

例: 毎回記事品質がぶれる、書式が混在する、エラー頻度が偏る、業務量が特定曜日に集中する。平均だけではなくばらつきと最悪時の品質を確認する。

## ムリ

例: 締切に依存する過密作業、過度な集中・記憶要求、保守不能な1人依存、レビュー工程の省略を強いる要求。削減後の仕事量が別の担当者へ丸投げされる場合、それは改善でなく負荷移転。

## ボトルネックと判定の作法

- どの制約が全体のスループットを止めているかを先に確認。見た目の工程数が多いだけで最優先問題とは限らない。
- 個別作業を高速化しても上流・下流が滞れば全体改善にはならない。
- 確認済み／利用者報告／仮説を分け、欠けた根拠が改善判断に不可欠なら追加情報を求める。
- 「改善なし」という判定も正当な成果。変更のための変更を禁じる。
